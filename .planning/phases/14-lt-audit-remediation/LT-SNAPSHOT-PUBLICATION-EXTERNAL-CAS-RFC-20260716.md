## Required trust boundaries

Four identities are mandatory. Their active and historical keyrings are
globally disjoint and captured as one startup trust registry:

1. Acquisition authority signs provider receipts and the input contract.
2. Offline IT bootstrap authority signs one exact, short-lived, one-shot legacy
   authorization and has no publisher, acquisition or anchor credentials.
3. Data publisher signs a publication intent/event but cannot sign or mutate
   the external anchor head.
4. IT anchor service owns the domain-wide compare-and-append operation, anchor
   signing key and monotone head. Its private key and write credentials are not
   available to the publisher, model runner, candidate assembler or promoter.

The authoritative external object is a signed CAS receipt, not a local event
chain. The production anchor backend must provide authenticated `get_head`,
`compare_and_append`, operation lookup and signed head observations. A local filesystem
backend is test-only and reports `UNSUPPORTED`; a directory of signed files is
not sufficient without independently enforced CAS plus immutable retention.

The canonical contracts are:

- `lt_snapshot_publication_intent.v1`, signed by the publisher request
  authority and binding the operation, expected head, generation inventory,
  contract and optional legacy pointer;
- `lt_snapshot_bootstrap_authorization.v1`, signed only by the offline IT
  bootstrap authority and embedded byte-for-byte in the sequence-1 intent;
- `lt_snapshot_anchor_receipt.v1`, signed only by the external service and
  binding sequence, predecessor, operation and exact intent hash;
- `lt_snapshot_anchor_head_observation.v1`, signed by the external service for
  a caller challenge and binding the current receipt, sequence and expiry.

## State machine

### PREPARE

- Verify the signed v2 acquisition bundle, replay, exact inventory and EEX
  vintage closure.
- Copy into a private operation staging directory and revalidate immediately
  before and after the immutable generation rename.
- Build one canonical signed publication intent containing `operation_id`,
  publication domain, generation and contract hashes, expected predecessor,
  operation timestamp and event type.
- Persist the immutable intent. Do not change `current.json` and do not
  claim a commit.

Result: `PREPARED_NOT_COMMITTED` plus exact request/event hashes.

### EXTERNAL CAS

- The anchor service authenticates the intent and checks the domain binding.
- `compare_and_append(expected_head, event_id, pointer_sha256, operation_id)`
  executes under a domain-wide lock/CAS shared by every host and data root.
- An exact retry returns the original receipt. Reuse of `operation_id` with any
  different input is a permanent conflict.
- The service durably appends and returns a signed receipt containing sequence,
  previous head, event, pointer, operation, domain and commit timestamp.

The publisher persists only the receipt at this phase. It does not request or
persist a HEAD observation. Result:
`COMMITTED_EXTERNAL_CAS_AWAITING_FRESH_HEAD` only after durable acknowledgement
or exact operation recovery from the external backend.

### FINALIZE

- Perform exact operation lookup, then obtain a signed, expiring head
  observation for a fresh caller challenge on every retry.
  Verify the receipt with the anchor-service trust registry and require the
  observation to select that receipt before projecting it as current.
- Verify the event, immutable generation and pointer bytes again.
- Atomically project `current.json`. A projection failure after external CAS is
  reported as `COMMITTED_REPAIR_REQUIRED`, never as an uncommitted operation.
- Archive each observation immutably as `<observation_id>.json`. An expired
  prior observation is retained as history and never blocks renewal.
- An exact retry repairs or returns the existing projection without a new
  event or CAS receipt.

## Candidate and capstone evidence

The candidate archive must include exact bytes and hashes for:

- publication intent;
- external anchor receipt;
- authoritative head/inclusion proof captured at run start;
- data pointer and input contract.

Candidate assembly verifies all four authorities and their transitive
bindings. Capstone verifies the archived proof, replays the candidate bundle,
and queries the external backend to prove that the archived receipt remains in
the authoritative history. A signed acquisition contract plus a fabricated
pointer is never sufficient.

## Mandatory attacks

- Delete the latest anchor and restore the previous pointer.
- Delete all anchors and install a fresh signed genesis.
- Build a correctly linked alternative branch after truncation.
- Race two hosts/data roots on one publication domain.
- Lose the response after successful external CAS and retry exactly.
- Reuse an operation ID with another generation, contract or predecessor.
- Kill after event, immutable generation, external CAS and pointer projection.
- Leave immutable-writer residue and stale staging operations.
- Rotate event and anchor keys while verifying historical receipts.
- Reuse an active or historical key across bootstrap, request, anchor,
  acquisition, time, journal or promotion roles.
- Crash after CAS but before local receipt, after receipt but before
  observation, and during receipt/observation persistence; recover an exact
  receipt or quarantine and replace a truncated local copy.
- Attempt legacy adoption with a wrong hash or calibration-eligible seed.
- Submit candidate/capstone evidence without the external anchor receipt.

## 2026-07-23 Windows container and CI contract amendment

This amendment industrializes publisher runtime v6 without changing the
external-CAS trust model. It supersedes any interpretation that a working
zipapp alone is a deployable publisher.

The only admitted container lane is Windows `amd64` under process isolation.
Builder and runtime use the same fully qualified digest-pinned base. CI checks
the host/base Windows major, minor and build compatibility, rejects base or
final `Config.Volumes`, and validates final `ContainerUser`, working directory,
entrypoint, empty command, disabled healthcheck and exact OCI/FMV labels. The
result is addressed by the immutable image ID emitted through `--iidfile`; no
mutable tag is an authority and this workflow does not push.

The build context is a positive list. `.dockerignore` admits exactly the 11
locked publisher wheel filenames, not `*.whl`, and excludes CT, Power BI,
model/data trees and environment files. A dedicated stager selects the exact
lock inventory, rejects links and unstable reads, records size/hash and
durably publishes a canonical manifest. CI re-audits that staging immediately
before the build from a fresh checkout and protected host Python. The image
then verifies the closure and receipts, all four CLI help surfaces, ACL write
denial/allowance, and a second internal build with byte-identical zipapp and
receipt.

Runtime mounts and lifecycle are contract data, not operator convention:

- scratch is the only general writable mount and no anonymous volume is
  allowed;
- input is read-only; phase-specific data and evidence mounts are explicit;
- secret directories must exist at container start, while the signing and mTLS

- `restartPolicy=Never`; exits `41` and `52` alone are retryable, with five

The context checker scans every regular context file and every decompressed
zipapp member for complete syntactic PEM/OpenSSH private-key blocks. It rejects
