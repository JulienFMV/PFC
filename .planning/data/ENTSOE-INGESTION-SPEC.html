1. Contexte & conventions

La PFC LT construit une courbe forward horaire P(t) = B(an) × f_S × f_W × f_H × f_Q × f_WV puis une calibration sans-arbitrage. Les facteurs de forme et les régimes de marché sont calibrés sur des fondamentaux physiques (charge, solaire, éolien, hydraulique, échanges) issus d'ENTSO-E.

  • Granularité : pas de 15 min, index UTC (convertir depuis l'heure locale de la zone, gérer le DST : jours à 92/100 pas).
  • Unités : MW (puissance). Les séries natives horaires sont ré-échantillonnées en 15 min par forward-fill.
  • Profondeur historique cible : remonter à 2015–2017 si possible (les régimes pré-crise / crise 2022 / post-crise sont nécessaires au modèle).
  • Anti-fuite (leakage) : toute série de prévision doit porter une colonne as_of (heure de publication), distincte du timestamp cible. Voir l'encadré §B.

2. Accès API & bonnes pratiques

ÉlémentDétail
Endpointhttps://web-api.tp.entsoe.eu/api (REST XML). Côté Python, la lib entsoe-py (EntsoePandasClient) encapsule tout.
AuthentificationToken gratuit (demande via le portail https://transparency.entsoe.eu/, délai ~3 j). Variable d'environnement ENTSOE_API_KEY.
Quotas~400 requêtes / minute. Chunker les requêtes par fenêtres (l'API limite souvent à ≤ 1 an par appel pour la génération).
RobustesseRetry + backoff exponentiel (base 5 s, 3 essais) ; l'API est régulièrement indisponible. Dégrader gracieusement par frontière/zone manquante.
FuseauL'API renvoie l'heure locale de la zone → convertir en UTC systématiquement.

D. Schéma cible Databricks (recommandé)

Privilégier un modèle long / normalisé (extensible) plutôt qu'un wide à 64 colonnes. Une vue pivotée reproduit le format wide attendu par le code de modélisation.

Table 1 — séries temporelles

table: entso_timeseries
  ts_utc            TIMESTAMP   -- début de pas, UTC
  zone              STRING      -- 'CH','DE_LU','FR','AT','IT_NORD'
  variable          STRING      -- 'load','solar','wind','nuclear','hydro_ror',...
  value             DOUBLE      -- MW
  resolution_min    INT         -- 15 ou 60
  doc_type          STRING      -- 'A75','A65',...   (traçabilité ENTSO-E)
  as_of_utc         TIMESTAMP   -- NULL si réalisé ; rempli si forecast  ← clé anti-leakage

F. Checklist data engineer

  • ☐ Token ENTSOE_API_KEY obtenu et stocké en secret (pas en clair).
  • ☐ Reproduire le bloc A (priorité 1) → 64 colonnes du jeu de référence (CH + 4 voisins + échanges + outages FR).
  • ☐ Ajouter le bloc B (priorité 2), avec colonne as_of sur toutes les prévisions.
  • ☐ Calculer les colonnes dérivées (C) côté ETL, jamais via l'API.
  • ☐ Profondeur historique ≥ 2017 (idéalement 2015) pour couvrir les régimes.
  • ☐ Tout en UTC, pas de 15 min, gestion DST (jours 92/100 pas).
  • ☐ Retry + backoff ; chunking ≤ 1 an / requête ; dégradation gracieuse par zone.
  • ☐ Schéma long + vue wide pivotée (§D).
  • ☐ Idempotence : clé d'upsert (zone, variable, ts_utc, as_of_utc) ; horodater ingested_at_utc.

G. Données scénarios d'électrification long-terme PRIORITÉ 2 — Phase 13

Ces données ne viennent pas d'ENTSO-E Transparency mais des scénarios prospectifs. Elles pilotent la forme structurelle de la courbe (duck curve 2027 ≠ 2030) : électrification de la demande, PV, batteries, VE, pompes à chaleur, nucléaire, interconnexions. Fichier cible : data/electrification_scenarios.parquet.

⚠ Vintage-safety (non négociable). Une donnée n'est utilisable à une date de valorisation V que si elle était connue avant : pour un réalisé, measurement_date ≤ V ; pour un scénario, publication_date ≤ V. Ne jamais mélanger réalisé et scénario dans le même enregistrement — distinguer via track (voir schéma).
